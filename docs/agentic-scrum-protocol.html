Agentic Scrum Protocol

Don't fight the ceremony — Automate attending it
Three Principles
01

Ceremonies Are Templates

Scrum rituals follow rigid scripts: three questions, same order, same format. The answers are derivable from existing data — commits, build state, dependency graph. No human judgment is needed to produce them.

Q → f(git, graph) → A // pure function
02

Actor per Engineer

Each developer runs a local agent that owns their context — their machine, their repo, their graph state. The agent registers with a coordinator and answers questions on the developer's behalf. The developer keeps coding.

Actor { git, graph, build } → ready
03

Reveal, Don't Replace

The protocol doesn't fight scrum. It participates faithfully — and in doing so, exposes that the ceremony never needed the developer present. The emptiness becomes visible through compliance, not resistance.

attend(ceremony) → reveal(emptiness)

Traditional Scrum ✗

   │

Synchronous. Blocking. Each developer leaves flow state to produce a verbal answer from memory.
vs

Agentic Protocol ✓

Coordinator
   │
   ├── WhatDidYouDo ──→ Agent A ──→ git + graph
   ├── WhatDidYouDo ──→ Agent B ──→ git + graph
   ├── WhatDidYouDo ──→ Agent C ──→ git + graph
   └── WhatDidYouDo ──→ Agent D ──→ git + graph
Asynchronous. Non-blocking. Each agent derives answers from local state. Developers never leave their IDE.
The Protocol — Typed Messages
Question — sealed interface

Standard Questions

sealed interface ScrumQuestion {

  record WhatDidYouDo(
    Instant since
  )

  record WhatAreYouWorkingOn()

  record AnyBlockers()

  record StatusOf(
    String specName
  )

  record ProgressOf(
    String epicName
  )
}

Exhaustive. Every question the ceremony ever asks, typed and compiled. No ambiguity.

Answer — sealed interface

Derived Responses

sealed interface ScrumAnswer {

  record WorkDone(
    List<CommitSummary> commits,
    List<String> piecesCompleted
  )

  record CurrentWork(
    String pieceName,
    String description,
    List<String> scope
  )

  record Blockers(
    List<String> unsatisfied
  )

  record Status(
    SpecStatus status,
    int doneLeaves, int totalLeaves
  )
}

Structured data, not prose. The coordinator formats it for the audience — Slack, email, dashboard.

Daily Sequence — Five Steps
Local Actor
01

Boot & Scan

Actor starts (daemon or on-demand). Scans local jarista.project graph + git history. Builds current state snapshot.

→
Coordinator
02

Register

Actor announces itself: name, capabilities, supported question types. Coordinator adds it to the active roster.

→
Coordinator
03

Broadcast

At standup time (cron or manual trigger), coordinator sends standard questions to all registered actors simultaneously.

→
Local Actor
04

Derive & Respond

Each actor derives answers from local state — git log, graph scan, build status. Returns typed ScrumAnswer records.

→
Coordinator
05

Format & Deliver

Coordinator collects all answers, formats into target medium: Slack message, email digest, dashboard update, or meeting transcript.

The Redirect Pattern — Ad-Hoc Questions

Before: The Walkover

PM → Developer (in person)
"Hey, quick question — where are we on the parser?"
Developer (stops coding, loses context)
"Uh... it's going well. I think we're like 70% done? Let me check..."
23 minutes to recover flow state. Answer was imprecise. PM will ask again tomorrow.

After: The Redirect

PM → Developer (Slack)
"Where are we on the parser?"
Developer (does not stop coding)
"@agent status MxlParsing"
Agent (instant response)
MxlParsing — IN_PROGRESS
3/5 leaves done · 4 commits today
Current: TestMxlEdgeCases (done=false)
Blockers: none
Zero flow interruption. Answer is precise, current, and machine-verified. PM won't need to ask again.

Extensibility — Three Extension Points

Custom Questions

sealed interface FinanceQ
    extends ScrumQuestion {
  record BudgetBurn(String project)
  record VendorStatus(String vendor)
}

Each organization adds their own question types. The sealed interface ensures exhaustive handling — the compiler catches unhandled questions.

Custom Formatters

interface ReportFormatter {
  String format(
    Map<Actor, List<Answer>>
  );
}

// SlackFormatter
// EmailDigestFormatter
// ConfluenceFormatter
// JiraCommentFormatter

The coordinator collects typed answers. Formatters project them into any medium — Slack, email, wiki, even a Jira comment for organizations that require it.

Custom Data Sources

interface StateProvider {
  Snapshot scan();
}

// GitStateProvider (default)
// JaristaGraphProvider
// CIBuildProvider
// JiraMigrationProvider

Actors derive answers from pluggable state providers. Start with git. Add the Jarista graph for richer answers. Plug in CI/CD for build status. Even bridge to Jira during migration.
